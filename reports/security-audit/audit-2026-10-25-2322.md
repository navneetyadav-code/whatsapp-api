## 2. Detailed Vulnerability Breakdown

### Finding 1: Unrestricted File Upload Leading to Remote Code Execution (RCE)
- **Affected File:** `public/index.php` (Lines 75–110)
- **Vulnerability Type:** CWE-434: Unrestricted Upload of File with Dangerous Type
- **CVSS Score:** 9.8 (Critical)
- **Vulnerability Mechanism:**
  In `public/index.php`, the message sending route (`page=message-send`) processes attachments from `$_FILES['attachment']`:
  ```php
  $ext = strtolower(pathinfo($_FILES['attachment']['name'], PATHINFO_EXTENSION));
  $fileName = uniqid('media_') . '.' . $ext;
  $target = $uploadDir . $fileName;
  move_uploaded_file($_FILES['attachment']['tmp_name'], $target);
  ```
  The code takes the client-provided extension without validating against an allowed whitelist. If an attacker uploads a file with a `.php`, `.phtml`, or `.phar` extension, the file is saved directly into the public web root (`public/uploads/media_XXXXX.php`). An attacker can then directly request this file via HTTP and achieve arbitrary remote command execution (RCE) on the server. Furthermore, the application trusts the client-provided MIME type header `$_FILES['attachment']['type']` rather than inspecting server-side binary magic bytes.
- **Remediation Strategy (Planned):**
  1. Enforce a strict whitelist of permitted extensions: `['jpg', 'jpeg', 'png', 'gif', 'webp', 'pdf', 'mp4', 'mov', 'mp3', 'ogg', 'wav', 'csv', 'txt']`.
  2. Validate real file MIME type using PHP's `finfo_file(finfo_open(FILEINFO_MIME_TYPE), $tmp)`.
  3. Explicitly reject any file attempting to upload executable extensions (`.php`, `.phtml`, `.phar`, `.shtml`, `.cgi`, `.exe`).

### Finding 2: Path Traversal & Arbitrary Local File Exfiltration via Message Attachment Payload
- **Affected File:** `worker/server.mjs` (Lines 788–820)
- **Vulnerability Type:** CWE-22: Improper Limitation of a Pathname to a Restricted Directory; CWE-918: Server-Side Request Forgery
- **CVSS Score:** 8.6 (High)
- **Vulnerability Mechanism:**
  When the worker processes a queued message in `sendQueuedMessage`, it extracts `attachment.path` from the message payload:
  ```javascript
  const attachment = payload?.attachment;
  if (attachment?.path) {
    const fileStats = statSync(attachment.path);
    if (!fileStats.isFile()) ...
    outgoingMessage = { document: { url: attachment.path }, ...commonMedia };
  ```
  The worker only verifies that the file exists and is a file. It does not ensure that `attachment.path` is strictly contained within the intended `public/uploads/` directory. An attacker who controls or inserts message records can point `attachment.path` to sensitive files on the host filesystem (e.g., `.env`, `database.sql`, `C:\Windows\win.ini`, `/etc/passwd`). The Baileys worker will read the file and send it out over WhatsApp as a media document.
- **Remediation Strategy (Planned):**
  1. Validate that `attachment.path` resolves to a path strictly within the application's uploads directory using `path.resolve` and boundary verification (`normalizedPath.startsWith(uploadDir)`).
  2. Disallow arbitrary local file references outside storage.
  3. Clean up ephemeral temporary files in a `finally` block.

### Finding 3: Missing Authentication & Sensitive Queue Exposure in Test Script
- **Affected File:** `public/api_test_full.php` (Lines 40–47, 88–96)
- **Vulnerability Type:** CWE-306: Missing Authentication for Critical Function; CWE-200: Exposure of Sensitive Information
- **CVSS Score:** 7.5 (High)
- **Vulnerability Mechanism:**
  In `public/api_test_full.php`, the authentication guard `require_auth()` is commented out:
  ```php
  // If you want to keep the page behind authentication, uncomment the line below:
  // require_auth();
  ```
  The script then executes a direct database query:
  ```php
  $recent = Database::pdo()
      ->query('SELECT id, recipient, normalized_recipient, status, attempts, error_message, created_at, sent_at FROM message_queue ORDER BY id DESC LIMIT 8')
      ->fetchAll();
  ```
  Any anonymous internet visitor can navigate to `/api_test_full.php` and view the 8 most recent queue entries, leaking recipient phone numbers, message statuses, and error messages. It also leaks internal ngrok proxy tunnel URLs.
- **Remediation Strategy (Planned):**
  1. Uncomment and enforce `require_auth()`.
  2. Require local request verification (`is_local_request()`) to align with `test-page.php`.

### Finding 4: Cross-Site Request Forgery (CSRF) & State Manipulation on Session Control Endpoints
- **Affected File:** `public/session.php` (Lines 8–47)
- **Vulnerability Type:** CWE-352: Cross-Site Request Forgery (CSRF)
- **CVSS Score:** 8.1 (High)
- **Vulnerability Mechanism:**
  In `public/session.php`, `verify_csrf()` is only called when `$_SERVER['REQUEST_METHOD'] === 'POST'`:
  ```php
  $action = $_GET['action'] ?? 'status';
  if ($_SERVER['REQUEST_METHOD'] === 'POST') {
      verify_csrf();
  }
  if ($action === 'start') { ... }
  if ($action === 'logout') { ... }
  if ($action === 'sleep') { ... }
  if ($action === 'wake') { ... }
  ```
  However, actions `start`, `logout`, `sleep`, and `wake` are parsed directly from `$_GET['action']`. An attacker can embed an image or link (e.g. `<img src="https://hub.example.com/session.php?action=logout">`) on an external site. When an authenticated user triggers the request via GET, the worker executes a session logout, destroying session files (`rm(authDir)`) and disconnecting the linked WhatsApp device without CSRF protection.
- **Remediation Strategy (Planned):**
  1. Enforce that destructive state-changing actions (`start`, `logout`, `sleep`, `wake`, `send-test`) are only executed if `$_SERVER['REQUEST_METHOD'] === 'POST'`.
  2. Reject any state changes requested via `GET` method.

### Finding 5: Insecure IP Spoofing (Allowlist & Lockout Bypass) via Untrusted Proxy Headers
- **Affected File:** `src/lib/ApiCredentials.php` (Lines 121–143)
- **Vulnerability Type:** CWE-348: Use of Less Trusted Input in a Security Decision; CWE-290: Authentication Bypass by Spoofing
- **CVSS Score:** 6.5 (Medium)
- **Vulnerability Mechanism:**
  The `client_ip()` helper inspects client headers `HTTP_X_FORWARDED_FOR`, `HTTP_CLIENT_IP`, and `HTTP_X_REAL_IP` unconditionally:
  ```php
  foreach ($headers as $header) {
      if (!empty($_SERVER[$header])) {
          $ips = explode(',', $_SERVER[$header]);
          $ip = trim($ips[0]);
          if (filter_var($ip, FILTER_VALIDATE_IP)) {
              return $ip;
          }
      }
  }
  return (string) ($_SERVER['REMOTE_ADDR'] ?? '0.0.0.0');
  ```
  Because `client_ip()` trusts these headers without verifying whether `$_SERVER['REMOTE_ADDR']` is a trusted proxy, any external client can send arbitrary `X-Forwarded-For` headers. This allows bypassing:
  - API Key IP Allowlisting (`api_key_ip_allowed()`)
  - Login lockout protection (`login_lockout_seconds()`) by rotating spoofed IP headers
  - Development access guards (`is_local_request()`) by sending `X-Forwarded-For: 127.0.0.1`
- **Remediation Strategy (Planned):**
  1. Restrict proxy header evaluation so that `X-Forwarded-For` is only inspected if `REMOTE_ADDR` belongs to a trusted proxy or local loopback. Otherwise, fallback strictly to `$_SERVER['REMOTE_ADDR']`.

### Finding 6: Lack of Rate Limiting / Brute-Force Password Reset OTP
- **Affected File:** `src/pages/forgot-password.php` (Lines 77–102)
- **Vulnerability Type:** CWE-307: Improper Restriction of Excessive Authentication Attempts; CWE-640: Weak Password Recovery Mechanism
- **CVSS Score:** 7.4 (High)
- **Vulnerability Mechanism:**
  In `src/pages/forgot-password.php`, the OTP verification action (`action === 'verify_otp'`) verifies a 6-digit numeric OTP (`000000`–`999999`) against `password_resets`:
  ```php
  $stmt = $pdo->prepare("SELECT * FROM password_resets WHERE email = ? AND otp = ? AND expires_at > NOW() ORDER BY expires_at DESC LIMIT 1");
  $stmt->execute([$email, $otp]);
  $reset = $stmt->fetch();
  if (!$reset) {
      json_response(['ok' => false, 'error' => 'Invalid or expired OTP.'], 400);
  }
  ```
  Unlike `request_otp`, there is no attempt throttling or lockout on `verify_otp`. An attacker can submit automated OTP guesses against a target user's email within the 15-minute validity window to brute-force the 6-digit code and reset the victim's password.
- **Remediation Strategy (Planned):**
  1. Add rate limiting / failed attempt tracking on `verify_otp` (e.g. max 5 failed attempts per email before invalidating the reset token).

### Finding 7: SMTP Command & Header Injection in Raw Mail Socket Sender
- **Affected File:** `src/lib/Support.php` (Lines 187–239)
- **Vulnerability Type:** CWE-93: Improper Neutralization of CRLF Sequences; CWE-88: Improper Neutralization of Argument Delimiters in a Command
- **CVSS Score:** 5.3 (Medium)
- **Vulnerability Mechanism:**
  The `send_smtp_email()` function directly interpolates recipient and subject strings into raw socket SMTP commands:
  ```php
  fwrite($socket, "RCPT TO: <$to>\r\n");
  ...
  $headers = "From: $fromName <$from>\r\n";
  $headers .= "To: $to\r\n";
  $headers .= "Subject: $subject\r\n";
  ```
  Neither `$to` nor `$subject` are stripped of `\r` and `\n` characters. If untrusted input containing newline sequences is passed into `$to` or `$subject`, an attacker can inject arbitrary SMTP commands (e.g. extra `RCPT TO`) or arbitrary mail headers (e.g. `Bcc:` or MIME multipart headers).
- **Remediation Strategy (Planned):**
  1. Strip all `\r` and `\n` characters from `$to`, `$subject`, `$from`, and `$fromName`.
  2. Enforce `filter_var($to, FILTER_VALIDATE_EMAIL)` before initiating SMTP transactions.
