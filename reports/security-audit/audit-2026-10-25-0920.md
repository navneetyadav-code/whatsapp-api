## Executive Summary

A comprehensive automated security audit of the WhatsApp API Hub codebase was executed strictly on the `private-deploy` branch in compliance with the `private-deploy-security-auditor` skill. Four high-confidence vulnerabilities were detected across the PHP Gateway and Node.js Baileys Worker attack surfaces:
1. Full `127.0.0.0/8` loopback subnet, CGNAT, and IPv4-mapped IPv6 SSRF bypass in the Node.js worker webhook validator (`worker/server.mjs`).
2. Prefix-truncation directory traversal and arbitrary `.htaccess` execution-shield deletion in the Node.js worker media and session handlers (`worker/server.mjs`).
3. HTTP reverse-proxy header-spoofing localhost bypass and SSRF in developer test endpoints and API key allowlist validation (`src/lib/ApiCredentials.php`, `src/lib/Support.php`, `test/index.php`).
4. Time-of-check to time-of-use (TOCTOU) DNS rebinding and carrier-grade NAT (CGNAT) SSRF bypass in the PHP remote media downloader (`src/lib/Support.php`).

All vulnerabilities were remediated with surgical, backward-compatible security fixes adhering strictly to the **Architecture Preservation Constraint** with **zero architectural alterations**. All modified files were tested and verified with `php -l` and `node --check`, and all unit and contract test suites passed.

## Identified Vulnerabilities & Applied Remediation

### 1. SSRF & Loopback Subnet / IPv4-Mapped IPv6 Filter Bypass in Node.js Worker
- **Classification:** CWE-918 (Server-Side Request Forgery) / OWASP A10:2021
- **File Affected:** `worker/server.mjs` (`isPrivateIp()`, `assertSafeWebhookUrl()`)
- **Severity:** High
- **Vulnerability Mechanism:**
  In `isPrivateIp()`, private IP detection only checked exact string matches for `127.0.0.1`, `::1`, and `0.0.0.0`. It did not check the remaining `127.0.0.0/8` loopback block (e.g., `127.0.0.2`, `127.1.1.1`), `100.64.0.0/10` (Carrier-Grade NAT / Cloud VPC addresses), or IPv4-mapped IPv6 representations (`::ffff:127.0.0.1`, `::ffff:169.254.169.254`, `::ffff:10.0.0.1`). An attacker configuring a webhook target URL could supply an IPv4-mapped IPv6 address or alternative loopback IP to bypass `assertSafeWebhookUrl()` and induce the worker to send requests to local worker endpoints (`http://127.0.0.1:3107/sessions/...`) or cloud instance metadata services (`169.254.169.254`).
- **Remediation Applied:**
  Updated `isPrivateIp()` in `worker/server.mjs` to strip bracketed IPv6 formatting, unwrap `::ffff:`-mapped IPv4 addresses for recursive validation, and rigorously enforce subnet boundaries for `127.0.0.0/8` (loopback), `169.254.0.0/16` (link-local/cloud metadata), `100.64.0.0/10` (CGNAT), `0.0.0.0/8`, `198.18.0.0/15`, IPv6 unique local (`fc00::/7`), and IPv6 link-local (`fe80::/10`).
- **Verification Status:** Passed Node.js syntax verification with `node --check worker/server.mjs`.

### 2. Prefix-Truncation Path Traversal & `.htaccess` Execution Shield Deletion in Worker
- **Classification:** CWE-22 (Improper Limitation of a Pathname to a Restricted Directory) / CWE-284 (Improper Access Control)
- **File Affected:** `worker/server.mjs` (`sendQueuedMessage()`, `cleanupEphemeralMedia()`, `startSession()`, `/sessions/:userId/logout`)
- **Severity:** High
- **Vulnerability Mechanism:**
  1. Directory containment checks used `resolvedPath.startsWith(allowedUploadsDir)` without trailing path separator enforcement. Any sibling directory sharing the same prefix (e.g., `public/uploads_backup/` or `uploads-temp/`) was accepted as inside `public/uploads`.
  2. `cleanupEphemeralMedia()` unlinked any file located inside `public/uploads/` marked as temporary without verifying that the file was not a server configuration guard. An attacker supplying `public/uploads/.htaccess` as an ephemeral attachment path could trigger its deletion upon message delivery or terminal failure, destroying the `.htaccess` execution guard that denies PHP script execution in the uploads directory.
  3. Session path checks in `startSession()` and `/sessions/:userId/logout` similarly used `authDir.startsWith(SESSION_DIR)` without directory separator delimitation.
- **Remediation Applied:**
  1. Enforced directory boundary separation using `(resolvedPath === allowedUploadsDir || resolvedPath.startsWith(allowedUploadsDir + sep))` and `(authDir === SESSION_DIR || authDir.startsWith(SESSION_DIR + sep))`.
  2. In `cleanupEphemeralMedia()`, added an explicit check prohibiting deletion of `.htaccess` or any dot-file (`fileBase !== '.htaccess' && !fileBase.startsWith('.')`).
- **Verification Status:** Passed Node.js module parsing with `node --check worker/server.mjs`.

### 3. Header-Spoofing Localhost Bypass & SSRF in Dev API Tester
- **Classification:** CWE-290 (Authentication Bypass by Spoofing) / CWE-918 (Server-Side Request Forgery) / OWASP A01:2021
- **Files Affected:** `src/lib/ApiCredentials.php`, `src/lib/Support.php`, `test/index.php`
- **Severity:** High
- **Vulnerability Mechanism:**
  `is_local_request()` relied on `client_ip()`, which prioritized `HTTP_X_FORWARDED_FOR` over `REMOTE_ADDR`. An unauthenticated external client connecting directly to the server could send `X-Forwarded-For: 127.0.0.1`. `is_local_request()` evaluated to `true`, which in `test/index.php` bypassed all private and loopback IP blocking (`(!$isLocal && ...)`). This allowed external attackers to supply `http://127.0.0.1:3107/...` or internal database ports to the test endpoint and read internal responses. Additionally, direct external callers could spoof `X-Forwarded-For` to bypass API key IP allowlists (`api_key_ip_allowed()`).
- **Remediation Applied:**
  1. Hardened `client_ip()` in `src/lib/ApiCredentials.php` to only trust proxy forwarding headers (`HTTP_CF_CONNECTING_IP`, `HTTP_X_REAL_IP`, `HTTP_X_FORWARDED_FOR`, `HTTP_CLIENT_IP`) if the connecting socket (`REMOTE_ADDR`) is a trusted proxy or loopback IP (`127.0.0.1`, `::1`, or private subnets).
  2. Updated `is_local_request()` in `src/lib/Support.php` to require that `REMOTE_ADDR` be loopback/private and that any forwarded client IP also originate from a genuinely local address.
  3. In `test/index.php`, stripped bracketed notation from IPv6 addresses (`[::1]`) and inspected `CURLINFO_PRIMARY_IP` after connection to ensure non-local requests cannot target restricted internal hosts.
- **Verification Status:** Passed PHP syntax check with `php -l src/lib/ApiCredentials.php`, `php -l src/lib/Support.php`, and `php -l test/index.php`.

### 4. TOCTOU DNS Rebinding & CGNAT SSRF Bypass in Media Fetcher
- **Classification:** CWE-918 (Server-Side Request Forgery) / CWE-367 (Time-of-Check to Time-of-Use / TOCTOU)
- **File Affected:** `src/lib/Support.php` (`is_private_ip()`, `download_remote_media()`, `assert_safe_media_url()`)
- **Severity:** High
- **Vulnerability Mechanism:**
  1. `is_private_ip()` relied on `FILTER_FLAG_NO_PRIV_RANGE`, which does not filter RFC 6598 Carrier-Grade NAT (`100.64.0.0/10`) or benchmarking (`198.18.0.0/15`) addresses commonly used for internal cloud networking and VPC metadata endpoints.
  2. `download_remote_media()` validated the hostname's DNS records before dispatching cURL. However, an attacker using DNS rebinding with zero TTL could return a benign public IP during the pre-check and resolve to `127.0.0.1` or `169.254.169.254` during `curl_exec()`. Because `download_remote_media()` did not inspect `CURLINFO_PRIMARY_IP` after the TCP handshake, the internal payload would be written to storage.
- **Remediation Applied:**
  1. Expanded `is_private_ip()` in `src/lib/Support.php` to validate IPv4-mapped IPv6, strip brackets from IPv6 hostnames, and block `100.64.0.0/10`, `198.18.0.0/15`, and `0.0.0.0/8`.
  2. In `download_remote_media()`, added connection-time IP verification using `curl_getinfo($ch, CURLINFO_PRIMARY_IP)`. If the actual established socket connected to a private/reserved IP, the temporary file is unlinked and the request aborted immediately.
- **Verification Status:** Passed PHP syntax check with `php -l src/lib/Support.php`.
